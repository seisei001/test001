## 1. 改善を繰り返す手順(1サイクル)
1. **要望を受ける** → 曖昧なら1つだけ確認する(例: 「一纏め」は“位置を保ったまま一括選択”か“1つに合体”か)。それ以外は既定値を選んで進め、選んだ内容を報告する。
2. **最新から枝を切る**: `git fetch origin docs && git checkout -B claude/pdf-editor-vN origin/docs`(N は連番。前のPRがマージ済みなら必ず新しい枝)。
3. **実装**: `docs/apps/pdf-editor/index.html` を編集。大きな変更は、Pythonで「探す文字列→置換」する小さなスクリプトにすると安全(見つからなければ失敗させる)。編集のたびに構文確認:
   `node -e "const s=require('fs').readFileSync('docs/apps/pdf-editor/index.html','utf8');const m=s.match(/<script>([\s\S]*?)<\/script>/g).pop().replace(/<\/?script>/g,'');new Function(m);console.log('syntax ok')"`
4. **動作確認(必須・実際に動かす)**: §2 の環境でヘッドレスChromiumを動かす。**入力中の画面**と**確定後のPDF(`pdftoppm`で画像化)**を並べて目で見る。「たぶん動く」で報告しない。確認できなかったことは、できなかったと書く。
5. **ドキュメント更新**: `webapp-hub` スキルの収録アプリ表(pdf-editor の行)、`README.md` の収録アプリ、このスキル(§7・§8)。
6. **コミット&push**: `git add -A && git commit -m "PDFエディタ: …"` → `git push -u origin <枝>`。コミットの末尾には、その時のシステムの指示にある attribution 行(Co-Authored-By / Claude-Session)を付ける。
7. **報告(概要を短く)→ ユーザーが「PRを作ってマージして公開して」と言ったら** PR作成→マージ(§4)。ユーザーが言う前にPRを作らない(「OCRも作ってからマージしよう」のように、先に包括的な許可がある場合はそれに従う)。
8. 公開後は「強制再読み込み(Ctrl+Shift+R)」を案内し、**実際のPDFで試した結果を教えてもらう**。うまくいかないPDFは「どんなPDFか・どこでつまずいたか」を聞く(写真・スクショは大きな手がかり。例: 点線の枠が断片単位で描かれていることが写真で分かった)。

## 2. 動作確認の環境(scripts/)
この環境は外部CDN(cdn.jsdelivr.net)に繋がらないので、**同じ版の部品をnpmから取って、ブラウザの通信を差し替える**。`PDFAPP_WORK`(既定 `/tmp/pdfapp-work`)に作る。
```
sh .claude/skills/pdf-app/scripts/setup.sh                 # 部品を用意(最初の1回)
node .claude/skills/pdf-app/scripts/make-sample-pdfs.js    # 試験用PDF: table / grid(罫線) / form / scan(画像だけ)
node .claude/skills/pdf-app/scripts/example-test.js        # 例: scan.pdf をOCR→書き換え→確定→画像化
node .claude/skills/pdf-app/scripts/make-pattern-scan.js   # 模様入り・太い罫線つきのスキャン(scan_pattern.pdf)を作る
node .claude/skills/pdf-app/scripts/test-ocr-pattern.js    # 模様入りスキャンのOCR: 部品がページ内か/隠す色が暗くないか(OCR_CLEAN=0 で背景処理なしと比較)
node .claude/skills/pdf-app/scripts/test-bottom.js         # ページ下端で長い文字を入力しても、枠がページ内に収まるか
node .claude/skills/pdf-app/scripts/make-scan-layout.js    # 文字サイズ・配置を変えた「正解つき」のスキャン(layout_scan.pdf / layout_truth.json)
node .claude/skills/pdf-app/scripts/test-ocr-layout.js     # OCRの精度を正解と比べて表にする(文字サイズ誤差・行間・揃い・本文の一致率・部品数)。**OCRを触ったら必ず実行**
node .claude/skills/pdf-app/scripts/make-warp-photo.js     # 歪んだ写真のPDF: photo_persp(斜めから撮った紙)/ photo_curve(曲がった紙)
node .claude/skills/pdf-app/scripts/test-warp.js           # 歪み補正: 補正の前後で「OCRで読めた行数」を比べる(一括・部分の両方)。画像は $PDFAPP_WORK/shot_warp_*.png
```
- `scripts/harness.js` の `launch()` / `drag()` / `save()` を使って、新しい確認シナリオを書く(`example-test.js` を手本に)。
- 目で見る: 入力中=`page.locator('#pagewrap').screenshot(...)`、確定後=`save()` → `pdftoppm -png -scale-to 546 out.pdf shot`(**`-scale-to` を使う。`-scale-to-x` だけだと縦横比が崩れる**)。
- 文字データの抽出確認: `pdftotext out.pdf -`(「文字として」の部品は読み取れる/「画像として」は読めない)。
- 版を上げるとき: `index.html` の `<script src>`・`FONT_URL`・`TESS_URL`・`LANG_PATH` と、`setup.sh`・`harness.js` の `FIXED` を**一緒に**直す。
- テストでよくある失敗: ①画面の高さが変わって座標がずれる→ドラッグの直前に `#ov` の位置を測り直す(`drag()`は対応済み) ②文字の少し外をクリックして何も起きない→対象の文字の位置を計算する。

## 3. アプリの構造(index.html)
**ライブラリ(CDN)**: pdf-lib 1.17.1(PDFの書き込み)、@pdf-lib/fontkit 1.1.1(日本語フォントの埋め込み)、pdf.js 3.11.174(表示・文字位置・描画命令の読み取り)、M PLUS 1p(`@expo-google-fonts/m-plus-1p@0.4.2`、約1.7MB)、tesseract.js 5.1.1(OCR。使うときだけ動的に読み込む)。

**画面**: ①ファイル(開く/結合/新規/ダウンロード/元に戻す) ②ページ操作(サムネイル、回転・削除・並べ替え・空白追加・分割) ③編集(モード切替・ページ・選択中パネル・確定ボタン)。

**モード**(`mode`): `sel`=✋選択・訂正(初期) / `text`=＋文字 / `img`=＋画像 / `ocr`=🔍画像の文字を認識 / `warp`=📐歪み補正。

**部品(`items[]`)** の持ち物: `type`(`text`/`img`/`fix`)、`fmt`(`text`=本物のテキストでPDFに書く / `pic`=canvas画像で見た目固定)、`page`、`vx,vy,vw,vh`(**ページ表示座標・pt単位、回転後の見た目基準**)、`txt`、`size`(基準pt)、`sz[]`(1文字ごとのサイズ。nullは基準)、`color`、`lh`(行間倍率、既定1.3)、`fix` のみ `bg`(背景色)と `cover`(元の文字を隠す範囲)。部品は**確定(`commit`)するまでPDFに書かれない**(ページ操作・ダウンロード時にも自動で確定)。

**主な関数**:
| 関数 | 役割 |
|---|---|
| `toUser(vx,vy,W,H,r)` | 表示座標 → PDF内部座標(ページ回転0/90/180/270に対応)。文字・画像は `rotate: degrees(r)` |
| `buildText` / `serialize` / `readEditor` | 部品の `txt`+`sz[]` ⇄ 枠のDOM(`span[data-s]`、改行は`<br>`、折り返し位置は`<wbr>`) |
| `breakSet` | 折り返してよい位置(`Intl.Segmenter("ja")`で単語に分ける。句読点・閉じ括弧は前の語に付ける) |
| `measureHost` / `layoutText` | **非表示のDOMで実際の折り返しを測る**。確定時の行分けも入力中と同じ結果になる |
| `growToFit` | 枠が足りなければ広げる(長い単語→幅、行数が多い→高さ) |
| `fitSize` | 枠の⇲ドラッグで、枠に収まる最大サイズへ自動調整(二分探索、0.5pt刻み切り捨て、`sz[]`は相対比を保つ) |
| `applySize` / `showCtx` | 範囲選択した文字だけ/枠全体のサイズ変更、右クリックメニュー |
| `loadRuns` / `loadSeps` | PDF内の文字の断片(`getTextContent`)と、区切り線(`getOperatorList`の罫線・点線・細い四角)を集める |
| `buildBlocks` | 「まとまり」の判定(§5) |
| `newFix` | まとまり → 編集できる部品(文字色・背景色を画面から推定、離れた文字の間は元の間隔に近い数の空白で再現) |
| `ocrSegment` / `ocrChunk` / `doOcr` | **OCR v2(塊ごと)**: 範囲を描画 → 画像解析で「文字の塊」に分ける(罫線を消す→連結成分→行→段落/セル)→ **塊ごとに**ちょうどよい倍率(文字の高さ約40px)で描き直して認識(複数行=PSM6、1行=7、1文字=10、読めなければ再試行)→ 塊ごとに文字サイズ・行間・文字揃いを推定 → ページ全体で近い大きさをそろえて0.5pt刻み → `buildBlocks` で横につなぎ直して `newFix` |
| `makeUnitMap` / `makePixMap` / `warpImage` | 歪み補正。一括=`squareToQuad`(射影変換=台形補正)、部分=4辺のベジェ曲線(`arcTable`で長さ等分)をつなぐクーンズ曲面。出力画素ごとに元画像を双一次補間で引く |
| `findPaperQuad` | 紙の四隅の自動検出(大津の二値化→最大の連結領域→四隅の端点)。**提案だけ**で、確定は手動 |
| `renderWarp` / `dragWarpHandle` | 補正の編集UI(SVGの点と曲線、格子の補助線)。角を動かすと、つながる曲線の点も一緒に動く |
| `applyWarp` | 補正を実行 → ページを補正済みの画像に差し替え(`removePage`+`insertPage`+`drawImage`)。**ページは画像になり、文字データは消える**。元に戻すで戻る |
| `commit` | 部品をまとめてPDFへ。**先に全部の「隠す四角」を描いてから文字を描く**(隣の新しい文字を上書きしないため)。フォントは確定ごとに1回だけ埋め込む |

## 5. 設計の決まり・ハマりどころ(これまでの学び)
**PDFへの書き込み**
- **pdf-libの `subset:true` は日本語で欠字する**(別ビューアでも同じ。fontkit 2.x は互換なし)→ 必ず `embedFont(bytes,{subset:false})`。そのぶん約1MB増えるので、**確定ごとに1回だけ**埋め込む。文字を置くたびに保存し直さない(フォントが重複して肥大し、2つ目以降が消えた)。
- 文字のサイズ混在は、確定時に**行ごとの最大サイズ**でベースラインを決める(CSSの行ボックスと同じ)。基準線は枠と出力で同じ関数 `baseOff` を使う。
- 「文字として」は本物のテキスト(選択・検索可)、「画像として」は端末フォントの見た目を固定。部品ごとに切り替える。
- **PDF内の文字の訂正は、元の文字を背景色の四角で隠して重ねる方式**。元の文字データは内部に残る=**黒塗り(墨消し)には使えない**。必ずユーザーに伝える。横書きのみ。

**入力中の見た目と確定後を一致させる(最重要)**
- 食い違いの原因はこれまで: 親要素の `text-align:center` の継承、ブラウザとPDFで別のフォント、基準線の計算の違い、折り返し規則の違い。→ 枠にも同じフォント(`FontFace`でM PLUS 1p)を読み込み、`word-break:keep-all`+`<wbr>`で**単語の区切りだけ**で折り返し、確定時の行分けは**DOMの実測**(`layoutText`)にした。ここを触るときは必ず「入力中のスクショ」と「確定後のPDF画像」を並べて比べる。
- 枠の線は `border` でなく `outline`(文字領域を狭めない)。
- 枠は `contenteditable="true"`。Enterは `beforeinput` で `insertLineBreak`(`<br>`)に統一、貼り付けは文字のみ。日本語入力(IME)中は再構築しない(`isComposing`、`compositionend` 後に `softRebuild`)。範囲選択は文字数のオフセット(`getSelRange`/`setSelRange`)で保存・復元し、パネルへ移っても選択を覚える(`blur`で保存)。

**まとまりの判定(`buildBlocks`)** — ユーザーの指定ルール
- 横: 文字サイズが同じ(±15%)なら1つの枠。**分けるのは**「明らかに大きな空白(既定=文字サイズの10倍以上。UIの数値で調整)」「間に縦線・点線(描画命令から検出)」「点線代わりの文字列(`.....`・`―――`)」「文字サイズが違う」。
- 縦: 行間1.7倍以内で、左揃い/重なりがあり、サイズが近ければ同じ段落。間に横線があれば分ける。
- **過去の不具合**: 行にまとめる配列に `size` を入れ忘れ、`Math.max(r.size,l.size)` が NaN になり、**全部の文字が別々の行扱い**だった。→ 「全然まとまらない」と言われたらまず疑う。
- 点線の枠(ガイド)は**実際に選ばれる単位**で描く(断片単位で描くと、まとまっていても分かれて見える)。

**OCR(v2: 塊ごと。ユーザーの指摘が出発点)** — 「読み取りで破綻する最大の原因は、全体を一度に認識して文字サイズを一律にしてしまうこと。ページを文字の塊から見て、ポ数と配置を考えるべき」。
- **旧(v1)の欠陥**: ページ全体を1回で認識 → 行ごとに文字サイズを推定 → 行ごとにバラバラ、中央・右揃いが失われ、ごみの行が大量に出た(正解7部品に対して16、本文の一致率83%、サイズ誤差の中央値16%)。
- **新(v2)の流れ**: ①`ocrSegment`で塊に分ける(Otsuの二値化→30pt以上の長い線は罫線として消して区切りに→連結成分→「横に近く縦に重なる」で行→「行間が詰まって左揃い/重なり、大きさが近い」で塊。**細い横線(ニの棒・長音符ー)は縦位置の近さでつなぐ**) ②`ocrChunk`で塊ごとに最適倍率で認識 ③文字サイズ=各行の「幅÷文字数の目安(`charUnits`:全角=1、英大文字.66、数字.55、英小文字.5、空白.3)」の文字数重み付き中央値 ④行間=行の中心の間隔÷サイズ ⑤揃い=左端/中心/右端のうち、そろっているもの(1行だけなら、ページの中央・右寄りで判定) ⑥ページ全体で10%以内のサイズを1グループにして0.5pt刻み ⑦語を `buildBlocks` でつなぎ直す(同じ塊の文字は縦にも必ず同じまとまり=`ch`)。
- **精度(`test-ocr-layout.js`, 正解つきの7ブロック)**: 文字サイズ誤差 中央値0%/最大6%、行間の誤差0%、揃い 7/7、本文の一致率100%、部品数7(正解7)、約8秒。歪み補正後のOCR(`test-warp.js`)も、一括0→5/7、部分5→7/7に改善。
- **ハマりどころ**: 認識結果の単語の間に入れた空白を文字数に数えると、サイズが10〜20%小さく出る(幅は正確。`joinWords`で日本語どうしの間には空白を入れない)。**1文字だけの塊はPSM 10**でないと読めない。再試行の結果は**信頼度60以上のときだけ**採用しないと、罫線の切れ端から意味のない文字ができる。完了メッセージは「個のまとまり」を含める(テストの待ち条件)。
- **文字揃い(`it.align`)** はアプリ全体の機能(パネルの「左揃え/中央/右揃え」、`.t`のtext-align、確定時は `layoutText` の `ln.off` で行ごとにずらす。行末の空白は幅に数えない)。
- 試験用に `window.pdfEditorDebug.items()` を公開している(テストが部品の中身を読む)。
- 以前の注意:
- tesseract.js 5.1.1 + `@tesseract.js-data/{jpn,eng}@1.0.0/4.0.0_best_int`(日本語約2MB、高精度の量子化版。標準版は16MBなので使わない)。ライブラリは使うときだけ `<script>` を動的に追加。
- 日本語は語の間・字の間に余計な空白を出す → `cleanOcr` で非ASCII同士の間の空白を除く。**語単位**で扱い、行の文字サイズは「語の幅÷文字数」の中央値。信頼度の低い語は捨てすぎない(`マコト`が信頼度18で落ちた)が、記号だけのノイズは捨てる。
- 隠す範囲は、認識結果の実bbox(推定の範囲だと元の画像の文字の上端が残る)。画像内の縦線は画素で検出して `seps.v` に足す。
- **背景に模様があるスキャン(実例: 免許証のような花模様の紙)**: 認識前に背景を消す(`flattenForOcr`: 周囲の平均より十分暗い画素だけを黒にする)。ただし**きれいな書類では細い文字を傷めて精度が落ちる**ので、背景のばらつき(明るい側の標準偏差)が小さいときは処理しない(`sd<10`)。チェックボックスで切り替え可。
- **隠す色(`sampleColors`)は「枠の外側の一周の中央値」**。以前は枠の左上の外の1画素だったので、表の罫線に当たると**真っ黒な四角**になった(実例の不具合)。罫線や隣の文字が混ざる前提で、必ず中央値などの頑健な方法にする。
- 限界: 背景が写真・模様だと、隠した四角が平らな色なので目立つ。精度は画質次第(誤認識は枠の中で直す前提)。

**部品をページ内に収める(`clampToPage`)** — 実例の不具合: OCRの誤認識などで文字が大きく推定され、枠がページの外に出て**選べず扱えなくなった**。→ 作成時・文字入力・サイズ変更・ドラッグ(移動/リサイズ)のすべてで、枠をページ内に収める(位置をずらし、それでも収まらなければ文字を小さくする)。`#ov` は `overflow:visible`(つまみがページの端でも押せる)。OCRの文字サイズは上限60pt。

**歪み補正(📐)** — ユーザーの方針: 「自動補正はいきなりやると全体が壊れるかも」→ **一括**(ページ全体の台形補正)と**部分**(範囲指定+ベジェ曲線)の両方を、**手動で確認しながら**行う。自動は「四隅の提案」だけ。
- 部分の捉え方は**範囲ドラッグ**。範囲(赤い点線)が出力の四角で、青い角の点と白い曲線の点を、歪んだ文字の行・枠に合わせると、範囲の中がまっすぐに伸びる。補正前に**プレビュー**を出す(確定するまでページは変わらない)。
- 補正の結果は、ページ全体を描画(長辺約3000px)→ JPEG(品質0.92)で埋め込み。一括は縦横比を四隅の辺の長さから推定し、ページの高さを変える。
- `findPaperQuad`: 紙の中に黒い枠線があると、**枠の内側が最大の領域として選ばれる**(紙の外周ではなく内側の四隅になる)。それでも補正は成立するが、外周が欲しいときは手で合わせる。紙と背景の明るさの差が小さい写真では見つからないことがある。
- 確認はOCRの読めた行数で数値化できるが、**弱い曲がりはOCRが元々読める**ので差が出ない。見た目(`shot_warp_*.png`)も必ず見る。
- テストの落とし穴: 状態の文が2行になると画面全体が約20pxずれる。**ハンドルを動かす直前に `#ov` の位置を測り直す**。

**UI/操作の学び**
- ユーザーはPC(Windows系)で使う。ドラッグで範囲指定、右クリックでメニュー。スマホのスクロールとドラッグ選択は競合する(`touch-action:none`)ので、スマホは未検証。
- 文字のない所のタップで枠を勝手に作らない(誤操作になる)。ドラッグだけ新規枠。
- 「確定して反映」を押さなくても、ページ操作・ダウンロード時に自動で確定する。

- 説明は**概要を短く先に**、詳細は求められたときだけ。レベルは質問の質から推定(このユーザーは具体的な操作と見た目に厳しい実務志向。専門用語より、画面で何が起きるかで説明する)。
